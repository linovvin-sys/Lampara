Lampara, from database to sprite

Everything the system is made of and where to find it: the database, every endpoint, every page and module, the AI, the offline layer, the game and where the pixel characters come from, and every outside service and library.

Written from the working copy on 14 October 2026, including work not yet committed. Where something could not be verified it is said so in section 16.

1. What Lampara is

Lampara is a campus navigation web app for NCST. A visitor opens it in a phone browser (no install, no account) and gets to a building, or to a room inside it, using the camera and GPS outdoors and an animated floor plan indoors. An admin side lets staff draw the campus, register rooms and answer visitor reports.

Visitors

Pick a destination, follow the AR path outside, follow the animated floor-plan route inside, scan a door sign, search the directory, ask the AI, report a closed building or blocked path. Works offline after the first visit.

Admins

Register buildings and rooms with photos, draw outdoor walkways and indoor paths, calibrate floors for indoor AR, set doors, upload the campus map, review visitor reports, undo changes. Also works offline and syncs later.

Game layer

Points, weekly quests, achievements, a passport, a quiz, 13 pixel mascots, seasonal themes, music and sound effects. All stored on the visitor's phone.

How a request flows

  1. The browser asks for a PHP page. The service worker is network first: it uses the network when there is one, and a saved copy when there is not (10 second limit).
  2. The page's script calls an endpoint in Backend/api with fetch, sending and receiving JSON.
  3. Writes need an admin session. The same-origin check rejects a write that another website sent from an admin's browser.
  4. Directory data (buildings, rooms, graphs, floor plans) is copied into localStorage by student-offline.js, so the student pages can run with no signal.
  5. Anything personal (points, mascots, theme, trip in progress) never leaves the phone.

Design rules that hold everywhere

  • Network first. Online behaviour is the normal behaviour; saved copies are only a fallback.
  • No accounts for visitors. Nothing about a visitor is stored on the server, except an anonymous device cookie used only to limit abusive reports.
  • Server validates everything. The browser's checks are for convenience; the API repeats them.
  • The AI only answers from our data. It gets the directory as facts and must cite them; the server drops anything it cannot match.
  • Cache busting by file time. Every script and stylesheet link ends with ?v=<filemtime>, so a changed file is fetched at once.

4. Setting up and running it

  1. Database. Create lampara_db (utf8mb4) and import Backend/schema.sql. Tables created on first use (hazards, change log, settings) need nothing from you.
  2. Local settings. Copy Backend/db.example.php to Backend/db.php and fill in host, port, user and password. MAMP uses port 8889 and password root by default, XAMPP uses 3306 and none. This file is gitignored so teammates never overwrite each other's.
  3. Gemini key. Copy Backend/secrets.example.php to Backend/secrets.php and add GEMINI_API_KEY. Optional: GEMINI_MODEL (tried first), HAZARD_ALERT_EMAIL. Also gitignored.
  4. First admin. From a terminal: php Backend/scripts/create-admin.php. Never create admins through a web page.
  5. HTTPS on a phone. Camera, GPS and motion sensors only work on HTTPS. Use an ngrok tunnel to the local server while developing.
  6. Tailwind. Only needed if you add new utility classes: ./tailwindcss-cli -i Frontend/assets/css/input.css -o Frontend/assets/css/tailwind.css --minify (the binary is gitignored; download your OS version).

Rules worth knowing

  • Room numbers are unique per building, not school-wide. The key is room_building_number (building_id, room_number). Amafel 1101 and NCST-IIRT 1101 can both exist. The first write after an upgrade swaps the old room_number_unique key for the new one automatically (ensure_room_number_key() in room_number.php).
  • Room numbers have one canonical form ("1101 - A"), applied on every write. Lookups ignore case, spaces and dashes.
  • Positions on floor plans are percentages (0-100) of the image, so they stay right at any display size. Outdoor positions are real GPS.
  • Cascades: deleting a building removes its rooms, floor plans, paths and flags. Deleting a path point unlinks any room or building that used it.
  • Photos are files under Frontend/assets/photos/{buildings,rooms,hazards}/; the table stores only the path. That folder is user data and is gitignored.

Known drift in schema.sql

The file still shows the old global unique key on rooms.room_number and does not create the tables made on first use. A new install gets the right shape after the first write, but the file should be regenerated from a live database (SHOW CREATE TABLE for each table) the next time someone has a moment. This is the one place the documentation and the code disagree; the live database is the truth.

Security model

  • Reads are public, writes are admin. Students need the directory without logging in; every POST, PUT and DELETE (except visitor reports, flags, chat and scan) requires an admin session.
  • CSRF. A write whose Origin or Referer names a different host is refused. Requests with neither header (scripts, curl) pass, since they carry no browser cookie to abuse.
  • Passwords are stored as bcrypt hashes; login allows 8 wrong tries per address, then waits 10 minutes.
  • SQL. All user values go through prepared statements.
  • Photos. Only real images are accepted (bytes are checked, not the extension). Report photos must be JPEG, are redrawn in the browser, and have Exif and vendor tags stripped again on the server (so no GPS leaks from a hand-made upload). Uploaded photo folders have their own .htaccess.
  • AI cost control. Chat and scan are limited to 90 calls a minute per visitor; repeated first questions are answered from a 15 minute cache.
  • Secrets (db.php, secrets.php) are gitignored. The Gemini key never reaches the browser.

Visitor reports and trolling

hazards.php is the one public write that shows content to other people, so it is the most guarded:

  1. A new report is pending: only admins see it until one approves it.
  2. Urgent reports go live at once, marked "not yet checked by staff", but only with a photo, a GPS fix, the phone within 250 m of the chosen building (300 m of any building for a walkway report), and fewer than 2 urgent reports that day. Otherwise they wait like any other.
  3. Photos are hidden from the public until an admin confirms the report, so a bad photo never reaches students.
  4. Every photo is checked by Gemini first; nudity, gore, violence, hate symbols and non-place images are refused, never stored, and cost the phone a strike. If the check cannot run, the report just waits for an admin.
  5. Each phone: 5 reports per 10 minutes, 10 a day, no repeat of the same kind and building within 30 minutes. 2 strikes remove the urgent lane, 5 pause reporting.
  6. An admin deleting an unconfirmed report is what creates a strike.
  7. "Photo should not be here" notices count once per phone; three different phones return a report to the queue, but an admin-confirmed report cannot be taken down this way.

The phone is identified by a cookie, so clearing cookies starts a phone fresh; the per-address limit is the backstop.

Look and feel

  • Brand. Navy and yellow (NCST), Outfit for text, JetBrains Mono for numbers, Pixelify Sans for game headings.
  • Pixel style. Corners are cut with a stepped clip-path polygon (--px), buttons have an inset darker band at the bottom, strips use yellow dashes. Motion is limited to transform and opacity, and stops with prefers-reduced-motion.
  • Themes. Css/theme-vars.css defines --t-* colour variables. Every student stylesheet reads var(--t-x, #original), so the original colours remain the fallback. html[data-theme="halloween|christmas|newyear|valentine"] redefines them. Admin pages do not use themes.
  • No framework build. Edit a file, reload. Scripts are plain files, loaded with <script> in a fixed order.

8. How the main features work

Outdoor guide (guide-ar)

The start screen loads buildings and rooms, lets the visitor pick a destination, and on Start asks for camera, GPS and motion permission. locar-engine.js (LocAR.js on three.js) filters GPS fixes, holds the compass heading, and lays a chevron ribbon along the shortest route over the campus walkway graph (campus-route.js, Dijkstra) from the visitor to the building's entrance node. The status banner gives turn hints and distance, and "You have arrived" within 8 m of the entrance. A room or gate can be the target. Arriving awards points and a passport stamp.

Indoor route (journey)

One trip is a list of legs: inside to a room in the same building (one leg), or leave the building, walk outside, find the room (three legs). Inside legs run Dijkstra on that building's floor-plan graph (floor-route.js), across floors via stairs links, and are drawn on a canvas as a growing broken line with the equipped mascot walking it and footsteps. Before the first leg a room details card shows the photo, type, floor, hours and notes; a Room info button reopens it. The floor plan can be zoomed and panned. At the exit the card hands over to the outdoor guide with the next building already chosen, and a pop-up greets the visitor on arrival there. Finishing awards points and an orientation stamp when the room is one of the key offices.

Scan a sign

The camera frame is sent to scan.php, which asks Gemini for the room number only. The number is normalised and looked up. If the same number exists in more than one building the app decides which one: GPS clearly nearest to one of them (within 150 m and 40 m closer than the next), else the building of the last scan, else it asks "Which building are you in?". Typing a number follows the same path.

The AI chat

  1. chat_lib.php builds a compact list of facts: every room as [R12] 1101 Admission, 1st Floor, Amafel..., buildings [B#], campus gates [G#], and current visitor reports.
  2. The system prompt tells the model to answer only from those facts, in short plain sentences, and to return JSON with the ids it used.
  3. chat.php calls Gemini with a structured-output schema, trying gemini-3.5-flash then gemini-3.1-flash-lite (the "-latest" aliases stopped answering once, so real versions are pinned).
  4. The server keeps only ids that exist, removes any "[R#]" tags that leaked into the text, validates follow-up suggestions against the facts, salvages half-finished JSON, and adds room cards for rooms the reply clearly names.
  5. A first question is cached for 15 minutes (key includes the facts, so new data invalidates it).
  6. With no signal or no AI, chat-core.js answers from the directory on the phone using RoomSearch, and says so.

Search

room-search.js scores each word against room number, name, subtitle, initials ("hr", "osa"), building, floor and category, with one-letter typo tolerance, so "annex registrar" and "1101" both work. Gates are searchable through access-points.js.

Indoor AR and QR anchors

Indoor AR needs every floor on the route calibrated (real size and compass bearing of the plan). Steps are counted to move along the ribbon, with manual nudges. A QR anchor fixes the starting point. The outdoor guide and indoor guide were chosen after the AR Lab compared five engines (AR.js, LocAR, 8th Wall, WebXR, custom); that lab is kept in ar-lab/ and changes nothing in the app.

9. Offline

10. The game layer

Points and unlocks

  • Earning. 10 points per new building reached, 5 to 17 for the daily visit (it grows over a 7 day streak), tutorial steps, routes, scans, questions, the daily quiz, weekly quests, orientation stamps (15 each, 50 for all) and 22 milestone awards.
  • Spending. Mascots (20 to 1000) and seasonal themes (200, half price during the season). Points are total earned minus spent.
  • Weekly quests. Three picked each Monday from a pool of 13 (deterministic by week, so everyone has the same three). Progress counts real actions only.
  • Passport. A stamp per building really reached; the orientation trail for key offices (registrar, library, clinic, cashier, guidance, student affairs).
  • Quiz. Five questions a day from the real directory: which building a named office is in, which floor, building numbers. Generic rooms such as "Lecture Room" are never asked. Points once a day, practice any time.
  • Seasonal themes. Halloween (Oct 15 to Nov 2), Christmas (Dec), New Year (Dec 26 to Jan 7), Valentine (Feb 1 to 20). Each recolours the student UI and adds scene decorations (pumpkins and bats, snow and trees, fireworks, floating hearts).
  • Owner tools. A logged-in admin sees an "Unlock all mascots" button in the shop (it also unlocks every theme) for testing.
  • Tutorial. An interactive tour of about two dozen steps of the guide; it awards points per step.

All of this is in mascots.js (state and rules) and guide-mascot-shop.js (the shop UI), saved only in lampara_mascots. There is no server copy and no sync, so clearing browser data resets it.

11. Sprites and pixel art: where they are built

There are no image files for the characters or the scene. Pixel art is stored as text in JavaScript and drawn at runtime, which keeps it tiny, themeable and available offline.

Mascot sprites

  • Where: the LIST array in Frontend/Js/Include/mascots.js.
  • Format: each mascot has rows, an array of equal-length strings (16 rows of 16 characters, 48 for the mythic one). . is see-through; every other letter is a colour looked up in the shared palette PAL (for example k navy outline, y yellow, Y light yellow, w white). A mascot can add its own letters with pal.
  • Drawing: LamparaMascots.svg(id, size) turns the rows into an SVG, one rectangle per run of the same colour, shape-rendering: crispEdges. canvas(id) and draw() paint the same rows on a canvas (used by the walking mascot on the route page and the share card). Any <img data-mascot> is filled with the equipped mascot automatically.
  • Editing a mascot: change its rows, add it to LIST with an id, name, price, and a one-line blurb, and it appears in the shop. Keep every row the same length.

12. Music and sound effects

Everything is synthesised live with the Web Audio API in Js/Public/guide-audio.js. There are no audio files, so it works offline and costs nothing to host. A master compressor keeps the level steady.

  • Five music styles, each its own instrument and groove: dawn bells (bell arpeggios over a soft pad), drift lo-fi (electric piano, swung beat, vinyl crackle), dusk pads (slow wide pads, no beat), rain bossa (nylon guitar, walking bass, brushes) and porch ukulele (strums, shaker, a whistled tune).
  • Pools per screen. tour, start, where, pick, shop and route choose different styles, so each part of the app has its own mood.
  • Effects. click, blip, chime, stairs, footstep and the typing chirp used by the typewriter cards; game-feel.js adds a pop to every tap.
  • Mute. One shared preference (lampara_music) for the whole app. Browsers only allow sound after a first tap, so audio starts then.

Sound was tested only by checking that the code runs; it could not be heard in the automated browser. It still needs listening tests on real phones.

16. Known gaps and things to watch

  1. scan.php uses an alias model. It calls gemini-flash-lite-latest. The chat once hung on the same kind of alias and was moved to pinned versions with a fallback list. Give scan.php the same treatment before relying on sign scanning.
  2. schema.sql is behind the live database (section 5). Regenerate it.
  3. Game progress lives only on the phone. Clearing browser data or switching phones resets points, mascots and themes. This is deliberate (no accounts) but visitors should know.
  4. The campus fence is off on the development database. Turn it on for the real deployment if visitors must be on campus.
  5. Anti-troll limits rely on a cookie and a per-address cap. A determined person can still send some reports; the protection is that nothing reaches students unchecked except short, located, photographed urgent reports with the photo hidden.
  6. Photo check is a filter, not a guarantee. Admins should look at a photo before approving.
  7. Flaky inputs for AR. GPS and compass are the weakest part of the whole system. The path engine (locar-engine.js) has not been changed during the game work and needs outdoor testing on real phones.
  8. Duplicate room numbers across buildings are now allowed. The IIRT building must keep its building number empty, or the admin form's "starts with building number + floor" rule will reject its 1101 to 1103.
  9. Local file names. The Playwright tests assume a URL with a capital L; the local folder is lowercase.
  10. Not yet verified on a real phone: sound, install to home screen behaviour, camera scan end to end, GPS tiebreaker, pinch and double-tap zoom on the route plan, and the AR path.

17. Conventions for working in this codebase

  • Every API file starts with a comment that lists its methods, body and reply. Keep that true when you change it.
  • Do not put <style> or <script> blocks in pages; each page has its own .css and .js file.
  • New student colours go through var(--t-*, #fallback) so themes keep working. Admin CSS stays on its own colours.
  • Link scripts and styles with ?v=<filemtime>.
  • Never commit Backend/db.php, Backend/secrets.php or uploaded photos.
  • Copy in the app avoids em-dashes, purple and anything that sounds like marketing; messages say what happened and what to do.
  • When you change files that visitors cache, raise VERSION in Frontend/sw.js.
  • Anything that touches location, camera or personal data must be explained on the privacy page.
